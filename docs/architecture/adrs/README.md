# Architecture Decision Records

This folder contains Architecture Decision Records (ADRs) for Voice Support Bot.

ADRs capture structural decisions that should remain visible beyond code, chats,
diagrams, and planning notes. When a decision changes, create a new ADR and mark
the previous one as superseded instead of rewriting history.

> **Note (built vs target, refreshed 2026-08-05):** an ADR status of `Accepted`
> records an accepted **target decision**, not necessarily that it is implemented.
> As of the Sprint 11 branch (`feat/sprint-11-remote-deployment`):
>
> - **Built:** the two-service voice loop (ADR-0021/0022/0023/0024/0025/0033/0035),
>   the backend conversation engine, RAG and observability
>   (ADR-0001/0006/0007/0014/0026/0027/0028/0030/0031/0034), the pilot latency
>   taxonomy (ADR-0018/0029), **Redis-backed sessions** (ADR-0008, Sprint 11
>   TASK-BE-021), the **backend↔runtime Flow A SSE style** (ADR-0036), and the
>   **pilot deployment** stack (ADR-0038/0039).
> - **Target-only — NOT implemented in code yet:** billing/BSS
>   (ADR-0003/0004/0005/0017), **multi-agent routing** (ADR-0015 — no
>   `IntentClassifier`/`AgentProfile` on this branch), Genesys/escalation handoff
>   (ADR-0019/0020), omnichannel contracts (ADR-0009/0010/0011), and
>   **first-sentence streaming** (ADR-0037 — Accepted but shipped behind a
>   default-off flag, not yet enabled).
> - **Proposed (not decided/built):** ADR-0032.
>
> Implementation status is tracked in `product-backlog/backlog-index.md` and the

| [ADR-0033](ADR-0033-webrtc-single-live-voice-transport.md) | Accepted | WebRTC is the **single live (customer-facing) voice transport** for the web channel: all real-time turns (streaming STT in, streaming TTS out ≈ 360 ms first audio, barge-in with browser-native AEC) go through the `web_voice` WebRTC path (ADR-0022). A browser-facing WebSocket voice transport is **rejected** — it would duplicate the live path and drop native echo-cancellation/noise-suppression/jitter/Opus with no latency or quality gain (would reintroduce the ADR-0025 barge-in self-interruption). WebSocket stays the **server↔provider** streaming transport (voice-agent ↔ Gradium STT/TTS). The batch HTTP `/turn` path (≈ 14 s time-to-first-audio) is **offline/tests only**, retained as the deterministic QA/latency harness, never a live path. Web-only scope; telephony/Genesys media is out of scope. |
| [ADR-0031](ADR-0031-answer-language-handling.md) | Accepted | Answer language handling (TASK-BE-015): the assistant answers in the customer's question language (FR/EN) via an `AnswerLanguage` value object (detection heuristic + per-call LLM directive + hand-off markers) and a `LanguageDetector` domain service (per-turn, session stickiness, configurable default `en` for the Eir pilot). The decided language is threaded to the LLM adapter (directive appended last), the guardrail wording follows the same detector, `OutputGuardrail` matches every language's hand-off markers, and `voice_support.answer_language` + `[LANGUAGE]` logs make the per-turn choice observable. Closes the ADR-0030 answer-language open question. |
| [ADR-0034](ADR-0034-kb-audience-boundary-and-weak-confidence-clarify.md) | Accepted | KB audience boundary + weak-confidence clarify (BUG-005): a deterministic `AudienceClassifierPort` (`KeywordAudienceClassifierAdapter`) tags each article `customer`/`internal` at ingestion (JSONB `audience` metadata, defaults `customer`); `PgVectorStoreAdapter.search` always excludes `internal` on the customer answer engine (fail-closed, requires a full re-sync). `RetrievalConfidenceGuardrail` gains a `CLARIFY` band between the floor (`0.5`) and a clarify ceiling (`0.62`), and `InputGuardrail` clarifies vague/low-info continuers (`vas-y`…) before retrieval. Billing proof threshold (OQ-002) stays out of scope. |
| [ADR-0035](ADR-0035-conversational-end-of-call-on-customer-farewell.md) | Accepted | Conversational end-of-call on a customer farewell (US-041, TASK-WEB-010): a deterministic, no-LLM `ClosingIntentDetector` matches a config-tunable FR closing-phrase list as a word-boundary token subsequence, rejecting negations (`non, pas au revoir`) and closing words embedded in a longer request. On a standalone closing, a `CallEndFarewellProcessor` (inserted between STT and the answer step) speaks a confirmation ("Souhaitez-vous autre chose ?") and ends the call only on an explicit "done" confirmation **or** a bounded confirmation-scoped silence timer (`VOICE_FAREWELL_CONFIRM_TIMEOUT_S`, not a general silence-timeout — OQ-041-c stays out of scope); any other utterance cancels the farewell and is answered normally. Ending reuses the TASK-WEB-008 `drain()` path and records a `voice.call_end` reason (`customer_farewell` vs `client_stop`/`client_drop`) under the call correlation id. Phrase sets are FR, env-tunable (`VOICE_FAREWELL_*`). |
| [ADR-0037](ADR-0037-first-sentence-backend-streaming-to-tts.md) | Accepted | First-sentence backend answer streaming to TTS (TASK-WEB-015 lever 1): consume the backend **SSE** `converse-stream` on the Flow A per-turn path and hand the **first guardrail-passing, sentence-sized** chunk to the streaming TTS (plain `TextFrame`, barge-in unchanged) instead of waiting for the whole answer (~−700 to −900 ms). **Gated on DEC-002 safety**: a streamed sentence may be spoken only if the backend guarantees the stream is **vetted-only** (grounding + confidence gate passed) or carries an early authoritative confidence signal — otherwise the runtime does not speak partial content. Lever 2 (connect-time warm-up, mirror `TtsSessionWarmer`) recorded here, scheduled with the live pass; lever 3 (env-tunable end-of-turn hold) already implemented. |

| [ADR-0039](ADR-0039-embeddings-placement-and-provider-egress-tst.md) | Accepted | **Embeddings placement + provider egress on tst** (TASK-INFRA-003, addendum to ADR-0006/ADR-0038 §6): embeddings run on **Ollama `nomic-embed-text` (768 dim) as a CPU sidecar co-located per backend VM** (compose service, internal-only, model pulled at deploy) — no `vector_store` recreation, no cloud egress for RAG, no cross-VM hop/SPOF on the retrieval hot path. **Mistral embeddings rejected** for the pilot (1024-dim recreation + full re-sync + per-query cloud egress). Backend/ollama share the 8 GB VM (5 g/3.0 + 2 g/1.0). Only pilot egress: `api.mistral.ai:443` (chat), Gradium `:443` (STT/TTS), registry `:443` (pulls) — allowlist/proxy a platform input. |
| [ADR-0036](ADR-0036-backend-voice-runtime-communication-style.md) | Accepted | Communication style backend ↔ voice runtime: **Flow A** (live turn: transcript → answer → TTS, and intra-turn signals like the filler trigger) stays **synchronous request/response** over HTTP, using the backend's **SSE** stream (TASK-BE-007) for intra-turn streaming/signals on the *same in-flight request*; gRPC/WebSocket are the sanctioned evolution, **not** a broker. A **message broker (RabbitMQ/Kafka) is rejected on Flow A** (adds latency to a latency feature, RPC-over-broker correlation, at-least-once/ordering → filler after the answer or wrong turn) and **reserved for Flow B** (post-call/async/fan-out/omnichannel — targeted ~Sprint 12; RabbitMQ-vs-Kafka deferred to that ADR). The **filler phrase (TASK-WEB-019/US-020)** is broker-free: V1 = runtime-local `AnswerProcessor` timer + one generic phrase; tailored per-intent fillers = an early intra-turn event on the existing SSE stream (the split-arch equivalent of Pipecat `on_function_calls_started`). Port abstraction keeps a future Flow B broker an adapter change, not a rewrite. |
| [ADR-0040](ADR-0040-genesys-audio-connector-v2v-media-plane.md) | Accepted (target) | Genesys **Audio Connector** (the **bidirectional** feature of the AudioHook protocol) is the target V2V media plane, not bare AudioHook (the **Bot Transcription Connector** feature is listen-only). Splits the Genesys integration into three planes — **media** (Audio Connector, Architect Call Audio Connector action forks + pauses the flow), **control/routing** (Architect + Platform API owns transfer/queue on escalation), **context/handoff** (escalation payload on Architect variables / conversation attributes, backend-owned) — and records the Audio Connector constraints (premium, ≤5 integrations, one bidirectional stream/session, IVR channel, 15 min default cap, PCMU/L16 codecs) plus the overlap where Genesys-native barge-in/end-of-turn/playback events supersede the runtime's bespoke detectors (ADR-0025). Refines ADR-0020; NOT IMPLEMENTED (Sprint 13, gated by OQ-006). |
| [ADR-0042](ADR-0042-no-turn-for-pilot-genesys-audio-connector-external-media.md) | Accepted | **No STUN/TURN for the pilot.** Pilot validation proved the full server-side voice journey works VM↔VM and through the HTTPS edge, but external-browser WebRTC **audio** fails: with `VOICE_STUN`/`VOICE_TURN` empty the bridge only advertises its private host ICE candidate, unreachable off-subnet (signalling succeeds, media is silent). Provisioning a public TURN relay (coturn, public IP/DNS, UDP relay range, credentials) is **not justified** because the target external media plane is **Genesys Audio Connector** (ADR-0040) — a Genesys-initiated `wss://` AudioHook stream that needs no TURN. Decision: keep TURN unprovisioned; scope direct WebRTC (ADR-0033) to same-subnet/dev; deliver external audio via Genesys Audio Connector; keep a **WebSocket audio transport** as an interim lever only if a pre-Genesys external demo is needed. Refines ADR-0033/0040. |
| [ADR-0041](ADR-0041-postgres-schema-management-with-liquibase.md) | Accepted | Postgres schema is managed by **Liquibase YAML in the backend** (TASK-INFRA-009), superseding the implicit Hibernate `ddl-auto: update` + Spring AI `initialize-schema: true` + ad-hoc superuser SQL. Split by the connect-as-app-user constraint: **app schema** (`vector_store` reproducing Spring AI 1.0.0's exact DDL — `metadata json`, `embedding vector(768)`, `spring_ai_vector_index` HNSW cosine — + `kb_source_state`, guarded `not tableExists`/`MARK_RAN`) runs at **startup** as the app user (`ddl-auto: none`, `initialize-schema: false`); the **privileged bootstrap** (`CREATE EXTENSION vector`/`uuid-ossp` + grants) runs once at deploy Step 4 via a **one-shot `podman run liquibase`** superuser container with its own tracking tables; only `CREATE DATABASE`/`ROLE`/`ALTER … OWNER` stay a psql pre-step (Liquibase can't create the DB/role it connects as, and the app-user secret stays out of every changelog). Local dev creates the extensions via a pgvector init script. |
